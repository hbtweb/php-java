# PHPJava — the model

> Date: 2026-05-01.
> This document supersedes earlier framings in ROADMAP.md and
> ADJACENT-SHAPES.md where they conflict. It captures the
> architectural model reached through the design conversation
> 2026-04-25..2026-05-01.

## What PHPJava is

**A JVM-bytecode-to-PHP translator with selectable cache strategies.**

That's the whole shape. Everything else is implementation detail.

```
.class files
    │
    │  PHPJava: parse + decode + lower to PHP
    │
    ▼
PHP source
    │
    │  Zend Engine: parse + opcache + JIT + execute
    │
    ▼
CPU
```

The `.class` file is input. PHP source is the intermediate. Zend is the
runtime. PHPJava is the lens between them. **Thinner lens = faster.**

## Deployment modes — long-running is the primary target

PHPJava is designed for **long-running PHP processes** as the primary
deployment, not request-per-process FPM. Specifically:

- **Swoole** / **OpenSwoole** — coroutines + persistent state, HTTP
  servers, RPC services
- **AMPHP** / **Revolt** — async event-loop, fibers
- **RoadRunner** — long-lived PHP workers behind Go process manager
- **FrankenPHP** — long-running embedded SAPI
- **Plain CLI daemons** — `php long-running.php` for batch/queue/scheduler

The traditional CGI/FPM request-per-process model is supported as a
secondary deployment (it's where shared hosting lives), but design
decisions resolve toward long-running first.

**Why this matters:**

- **Compile cost amortises.** A 10ms AOT compile per-class becomes
  irrelevant after the first 1000 calls in the same process. In
  request-scoped FPM it would dominate.
- **JIT warm-up pays off.** Zend JIT (PHP 8.1+, `opcache.jit=tracing`)
  needs ~1000+ calls to a hot path before tracing kicks in and produces
  native code. Long-running processes get this; request-scoped doesn't.
- **In-process state is simpler.** Concurrency primitives (Swoole
  atomics, Fiber-based locks), connection pools, AOT caches all live
  in memory across requests.
- **Lazy AOT becomes the natural default.** No need to pre-compile at
  build time if the first-encounter compile happens once per process
  lifetime and serves all subsequent calls.

For request-scoped deployments (P1 with shared cPanel hosting), eager
AOT at deploy time is the right choice. The compiled PHP files are
opcache-cached across requests; per-request overhead is just the cost
of including the cached PHP — same as any normal Composer-installed
library.

## The three cache strategies are the same compiler

The compiler ("walk parsed bytecode → emit PHP") runs at one of three times:

| Strategy | When the compiler runs | What's cached | Per-call cost | Best for |
|---|---|---|---|---|
| **Eager AOT** | Build / deploy time | Emitted PHP files on disk | None — Zend executes the cached PHP | Request-scoped FPM, deploy-once-and-forget |
| **Lazy AOT** | First time a class is loaded | Emitted PHP in opcache / APCu / file / shared memory | One-time compile cost on first load | **Long-running processes (Swoole, AMPHP, RoadRunner)** — the default |
| **Interpret-fallback** | Per-call (no compile cache) | Parsed bytecode object (no PHP emission) | Bytecode walk per invocation | Cold methods called < ~10 times per process; runtime-generated bytecode that's about to be discarded |

**There is no separate "interpreter."** What we currently call the
interpreter is the degenerate case of "lazy AOT with TTL = 0 plus
in-memory execution instead of PHP emission" — i.e. compile to internal
state and execute, then discard. It earns its keep only for cold or
one-shot methods where the AOT-compile latency would exceed the savings.

The current PHPJava interpreter is a special case of the lazy strategy
where the "cache" is the parsed `JavaCompiledClass` object. It walks
opcodes via dispatch instead of emitting PHP. **Optimising it (Phase 2
spike) is moving it rightward on the cache axis** — pre-decoding,
hoisting, removing accidental costs. The endpoint of that motion is
"emit PHP and let Zend run it" — i.e., AOT.

So: **one compiler, three cache TTL choices.** In a long-running
process, Lazy AOT is the steady-state mode; Interpret-fallback covers
the remaining cold-method tail; Eager AOT exists for deploy-time
optimisation when you can predict the working set.

## Two peers on Zend

cljp (Clojure → PHP) and PHPJava (Java bytecode → PHP) are **siblings**,
not nested. Neither hosts the other. Both produce PHP that Zend
executes natively.

```
.cljp source                                  .class files
     │                                              │
     │  cljp compiler                               │  PHPJava
     │  (Clojure semantics                          │  (JVM contract
     │   → idiomatic PHP)                           │   → idiomatic PHP)
     │                                              │
     ▼                                              ▼
  ┌──────────────────────────────────────────────────────┐
  │                      Zend Engine                     │
  │     (parses PHP, opcache caches, JIT optimises,      │
  │      executes opcodes, refcount GC, all the work)    │
  └──────────────────────────────────────────────────────┘
                              │
                              ▼
                            CPU
```

When Clojure code needs to call Java code (or vice versa), they
**marshal at the language boundary** — a thin `cljp/java/bridge` shim.
Cost is paid only at the crossing.

This corrects an earlier framing that suggested PHPJava should adopt
cljp's `$GLOBALS`-as-runtime contract. That was wrong. cljp's runtime
serves Clojure semantics (PersistentVector, tagged strings, redefinable
Vars). Forcing Java values through it would distort Java semantics for
the dominant user (P1 below). The two runtimes stay independent;
interop is explicit.

## Personas — who PHPJava actually serves

| # | Persona | Deployment | What they want | Cared-about by current design |
|---|---|---|---|---|
| **P1** | PHP dev needs a Java library (PDFBox, Tika, iText, POI) on their existing PHP host | shared FPM | Idiomatic-PHP API into a Java JAR; eager AOT preferred | dominant for adoption |
| P2 | PHP dev wants Clojure | any | cljp serves them — not PHPJava | unaffected |
| P3 | Educator / curious about JVM internals | any | Readable interpreter / AOT output | bonus, not driver |
| P4 | Migration project (Java → PHP) | varies | Run Java + gradual rewrite | secondary |
| P5 | Polyglot dev (Clojure + Java libs) | **long-running (Swoole/AMPHP)** | bb-on-PHP equivalent | served by cljp + PHPJava + bridge |
| **P6** | Service developer running PHPJava as a daemon | **long-running (Swoole/AMPHP/RoadRunner/FrankenPHP)** | Lazy AOT; in-process state; long uptime | **primary target for design decisions** |

P1 is the largest *potential* user group; P6 is the **primary
deployment target the project is built around**. They're not in
conflict — design for long-running first (P6), and the eager-AOT
deployment path (P1) falls out as a build-time variant of the same
compiler.

Specifically:
- Java values map to natural PHP values (int → int, String → string,
  HashMap → idiomatic PHP class with ArrayAccess/Countable).
- No imposed redefinability (Java doesn't have it natively).
- No imposed wrapper objects beyond what Java semantics require.
- Native PHP debugging works (`var_dump`, IDE introspection).
- Long-running process state (Swoole atomics, fiber locks, AOT cache,
  connection pools) lives in process memory.

P1 is by far the largest group. **Design decisions resolve in P1's
favour when in doubt.** Specifically:
- Java values map to natural PHP values (int → int, String → string,
  HashMap → idiomatic PHP class with ArrayAccess/Countable).
- No imposed redefinability (Java doesn't have it natively).
- No imposed wrapper objects beyond what Java semantics require.
- Native PHP debugging works (`var_dump`, IDE introspection).

## Redefinability is a language concern

PHPJava the JVM has **no opinion** on whether values are redefinable at
runtime. Java code is dispatched directly (static after AOT, or via
PHPJava's classloader after lazy AOT). Languages that want
redefinability provide it themselves on top of PHPJava — same way
Clojure provides it on top of HotSpot.

Specifically:
- Plain Java: static dispatch, no redefinability infrastructure.
- Clojure on PHPJava: `clojure.lang.Var` (a Java class) provides
  indirection. PHPJava runs `Var` like any other Java class. Hickey's
  pattern works on PHPJava unchanged because the JVM extension surfaces
  it relied on (custom `ClassLoader` + `defineClass(byte[])` + Var
  classes) are JVM features, not HotSpot-specific.
- Hot-reload tools (JRebel-style): `Instrumentation.redefineClasses` —
  an extension surface PHPJava can implement when needed.

This keeps the JVM contract clean: one method = one PHP function (after
AOT) or one bytecode-walk (during interpret-fallback). No
indirection-by-default.

## All optimisation is subtraction

Every speedup identified in the design conversation removes a layer:

| Subtraction | What was removed | Speedup |
|---|---|---|
| Phase 2 hot-loop fixes | `microtime` per op, `new $opcodeClass()` per iter, `setParameters` chain, DI rebuild, `is_callable` × 2.25, `GlobalOptions::get` × 4.5, `BinaryReader` stream layer, primitive boxing | 5,220 ns/op → 22 ns/op |
| Naive AOT | the dispatch loop itself | 22 ns → 5.6 ns |
| Idiomatic AOT | the operand stack (replaced by expression trees) | 5.6 ns → 0.4 ns |
| **AOT total** | every layer between bytecode and Zend opcodes | **>10,000× faster than current** |

Apparent additions (caching, inlining, specialisation) are subtractions
in disguise — they remove repeated work, call overhead, runtime checks
respectively. The net effect is always: fewer cycles between intent and
CPU.

The discipline this implies: when writing or accepting a change, the
question is "what does this remove?" If the answer is "nothing — it
adds capability" then it's contract-completion (capability work), not
optimisation. The two tracks need different success criteria.

## What's optimisation vs what's capability

| Track | Test | Examples |
|---|---|---|
| **Optimisation** (subtraction) | Does this make existing things faster, with same observable behaviour? | Switch dispatch, opcode singletons, hoisted config, AOT |
| **Capability** (addition) | Does this make new things possible? | `defineClass(byte[])`, lambda metafactory, `Unsafe`, `String.indexOf` shim, `WeakReference` |

Both tracks proceed in parallel. Optimisation refines the lens;
capability extends what the lens covers.

## JVM extension surfaces — what languages above need

Languages on top of the JVM use specific extension surfaces. Each is a
capability PHPJava either implements or doesn't:

| Surface | What it gives | Used by | PHPJava status |
|---|---|---|---|
| Standard `ClassLoader` | Load `.class` from disk/JAR | All Java code | partial |
| `defineClass(byte[])` | Synthesize classes at runtime | **Clojure**, JRuby, Groovy, Spring AOP, mocking | **missing** |
| Reflection (`Class`, `Method`, `Field`) | Introspection, frameworks | DI containers, ORMs, JSON serializers, **Clojure internals** | partial stubs |
| `Unsafe` / Foreign Linker | C-level memory ops, atomics, CAS | Netty, Guava, JCTools, Disruptor | not present |
| `Instrumentation` (Java agents) | Runtime class redefinition, transformation | Profilers, JRebel, AspectJ | not present |
| `invokedynamic` + bootstrap methods | Pluggable dispatch | Lambdas, JRuby, Groovy 3+, modern Java/Kotlin/Scala | parsing only, no dispatch |
| Lambda metafactory | Synthesize functional interface impls | All Java 8+ code with lambdas | not present |
| JVMTI | Native debugging | JDB, IntelliJ debug | won't implement |
| JNI | Call C code | Native libs | won't implement (FFI substitute) |
| GraalVM Truffle | AST interpreter framework | TruffleRuby, GraalPython | n/a |

**The single most load-bearing capability gap for "run real Java
libraries" is the lambda metafactory** (most modern Java/Kotlin/Scala
hits it). For "run Clojure," it's `defineClass(byte[])`.

## Implementation strategies, behind one contract

PHPJava already has the right shape at the contract boundary
(`InvokerInterface`). Three implementations are possible behind it; the
classloader picks per-class:

```
                ┌─────────────────────────────────┐
                │  JVM CONTRACT                   │
                │  (ClassLoader + InvokerInterface) │
                └─────────┬───────────────────────┘
                          │
         ┌────────────────┼────────────────┐
         │                │                │
         ▼                ▼                ▼
  ┌─────────────┐  ┌─────────────┐  ┌─────────────┐
  │ Interpreter │  │  AOT'd PHP  │  │ Curated PHP │
  │ (universal  │  │  closures   │  │ shim        │
  │  fallback;  │  │  (eager or  │  │ (Packages/  │
  │  Phase 2    │  │  lazy)      │  │  java/*)    │
  │  optimised) │  │             │  │             │
  └─────────────┘  └─────────────┘  └─────────────┘
```

PHPJava already implements interpreter + curated shim. AOT is the
missing third. **The classloader is the dispatcher**: given a class
name, decide which implementation backs it.

Decision rule (proposal):
1. If the class is in `Packages/java/...` → curated shim
2. Else if a recent AOT cache hit exists → AOT'd PHP
3. Else if AOT-on-load is enabled → compile, cache, use AOT
4. Else → interpreter (with Phase 2 dispatch optimisations)

## Capability tier list — what to implement, in priority

Driven by P1's needs and Clojure-on-PHPJava ambition:

**T1 — required for any modern Java code:**
- Class file format up to Java 21 (`CONSTANT_Dynamic`, `Record`,
  `PermittedSubclasses`, `NestHost`, `Module`, `BootstrapMethods`)
- Lambda metafactory (`StringConcatFactory` + `LambdaMetafactory`)
- `String_` filled to Java 21 surface (~25 methods)
- Sequenced collections (3 interfaces + retrofits)

**T2 — required for many libraries:**
- Reflection API completeness (`Class`, `Method`, `Field`,
  `Constructor`, `Modifier`)
- `java.io.*` Reader/Writer/InputStream chain
- `java.util.regex.Pattern`
- `java.util.concurrent.atomic.*` (CAS — needs FFI or simulated locking)
- `java.util.concurrent.locks.*`
- `Thread.ofVirtual` / virtual threads (Fiber/Swoole adapter)
- `WeakReference` / `WeakMap` (PHP 7.4+ wrappers)

**T3 — required for Clojure:**
- `defineClass(byte[])` — runtime class loading from synthesised bytes
- ASM library (Java) running on PHPJava (uses no exotic deps)
- All of T1 + T2

**T4 — extension surfaces (later):**
- `Instrumentation.redefineClasses` (hot reload)
- `Unsafe` (or Foreign Linker)
- `JVMTI` (probably never)

**T5 — non-goals:**
- `java.awt`, `javax.swing`, `java.beans`
- JNDI, JAXB, javax.management
- Full bytecode verifier (trust the input)
- HotSpot-perf parity (we cap at ~50× HotSpot interpreted with optimal AOT)

## Optimisation tier list — what to subtract, in priority

Each is bounded work that gives measurable speedup. Starting from
current PHPJava (5,220 ns/op, ~10,000× HotSpot interp).

**O1 — Phase 0 baseline** ✓ (done; numbers in `bench/`).
**O2 — Test suite to green** (Phase 1 of original roadmap, ongoing).
**O3 — Hot-loop rewrite** — the H1–H8, M1–M4 list. Brings interpreter to ~22 ns/op. ~4–8 weeks.
**O4 — AOT compiler, naive level** — emit PHP per opcode, stack-as-array. Brings to ~5.6 ns/op. ~2–4 weeks once O3 lands. Compiler is a parallel `Aot/Emit/_*::emit()` tree mirroring the interpreter's `Kernel/Mnemonics/_*::execute()` tree.
**O5 — AOT compiler, idiomatic level** — decompile operand stack to expression trees, recognise loop patterns. Brings to ~0.4 ns/op. ~3–6 months. Requires a high-level IR (TeaVM-shape: SSA + CFG).

O3 and O4 share infrastructure (the same parsed bytecode walked
differently). O5 is a separate optimisation pass that adds a high-level
IR layer; the naive AOT continues to work as the fallback.

## What we don't need

This list is the contrarian half of the design — what we explicitly
*don't* build, despite some apparent appeal:

| Don't build | Why |
|---|---|
| **Shared `$GLOBALS` runtime with cljp** | cljp's runtime is Clojure-shaped; Java values would be distorted. Marshal at boundary instead. |
| **A separate IR for naive AOT** | JVM bytecode is the IR. PHPJava parses it. Walk and emit PHP. Add a TeaVM-shape IR only if/when O5 is needed. |
| **Universal redefinability via Var indirection** | Pay 10ns/call always, even when nobody redefines. Languages bring their own. |
| **Two parallel tracks ("interpreter optimisation" + "AOT compiler")** | They're the same compiler with different cache TTLs. One implementation, three cache modes. |
| **Full JVM verifier semantics** | Trust the input. Verifier costs more than it saves at our scale. |
| **PHP-source-to-bytecode** (existing `Compiler/Lang/Assembler/`) | Wrong direction for our goals. May keep for educational value; not a development priority. |

## Falsifier status, updated

The original ROADMAP.md falsifiers are revised by measurement:

| Falsifier | Original | Measured | Status |
|---|---|---|---|
| F1: per-op > 1µs after Phase 2 | "if true, abandon interp path" | 22 ns/op measured | **lifted** |
| F2: stub combinatorics blow up | unmeasured | TBD — needs probe | open |
| F3: concurrency model mismatch | unmeasured | TBD — depends on Swoole/FFI work | open |
| F4: bridge cost > 50µs | unmeasured | TBD — meaningful only after AOT lands | open |

F1's lifting is the most consequential change. The interpreter path is
viable. The AOT path is even more viable (5.6 / 0.4 ns/op measured).
Neither needs to be abandoned.
